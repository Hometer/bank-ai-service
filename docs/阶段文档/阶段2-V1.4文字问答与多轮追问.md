## 一、阶段目标

实现“当前非敏感问题 → 前置保护 → 有效公开上下文 → 规则/结构化模型判断 → 后端组织有来源的说明或具体缺口 → 原子保存 → 页面展示 → 继续、纠正、澄清或取消”的主链路。

范围对齐 T14-01–08；验收对齐 Q14-01–18，包括全部六类主题、部分可答、两次澄清、用户纠正、最多两个明确公开问题、对象标记、来源失效、在途竞态、持久化和失败体验。最多两个公开主题与现有 `ConsultationContext.topics` 上限一致；超过两个不截断为完整答复，提示分批咨询。

交付应包含本文件、代码、完整回归、真实模型验证、实际停止/启动恢复、桌面/手机截图、评分材料、README、项目状态及独立证据包。真实银行、自由生成金融解释、资金动作、账户权限、正式人工/投诉、音视频和云部署保持既定开通条件。

## 二、技术适配摘要

沿用现有架构和锁定依赖。模型仅输出资料编号与问题类别，后端决定候选、来源资格、缺口提示、答案正文、状态变化和权限。六条知识正文不扩写，导航/来源卡不变成办理步骤。模型请求只使用当前问题及最小有效主题，不取完整聊天历史。

保留 `/api/v1`、归属 Cookie、统一错误、会话版本条件更新及独立紧急提示。扩展既有 JSON 状态；无需新增关系表或迁移数据库引擎。原模型选择函数与解析器保留供旧契约回归；新版咨询使用独立、可区分的路由契约，复用现有预算和调用保护。

## 三、技术栈与模型

- Python 3.12.14、FastAPI、Pydantic、SQLAlchemy、Alembic、httpx、pytest、mypy、Ruff；原生 HTML/JS/CSS 和 Node.js 22.23.2。依赖版本不变。
- 模型沿用 D4：DeepSeek 官方 `deepseek-flash`、非思考模式、温度 0、结构化 JSON、输出最多 100 tokens。不增加供应商、Embedding、RAG、SDK 或工具。
- 默认规则模式无模型请求；真实模式的新咨询路由只在适用非敏感人工样例及同一台账限制内启用。
- 单条消息最多两次 HTTP 尝试，包含重试；400/401/403 等不可重试请求错误不重试，429/5xx、超时和结构错误允许一次剩余额度内的重试。客户端构造异常须被捕获，不泄露错误正文。
- 新路由设置整体 30 秒截止时间（包含初始化、连接、读取、校验和重试），每次网络阶段超时沿用配置默认 8 秒、最大 15 秒并受剩余总时限约束；截止后停止发起新尝试并返回模型不可用。页面保留 35 秒等待上限。该总截止机制为待实现要求，不把现有 httpx 分阶段超时声称为已具备整体截止。
- 输入沿用既有 5000 的保守预算边界：序列化 UTF-8 请求字节数加 512 的开销不得超过 5000；输出最多 100 tokens。每次预留 0.0108 元。输入超长在请求前失败，不截断成意思不同的问题、不扩大 policy。结构在此边界内无法得到有效结果时记待验，不增加输出额度。

## 六、数据、资产与状态

### 6.1 咨询上下文与旧数据

扩展 `conversations.context` JSON，不新增长期独立历史。新写入使用 `context_version=2`，字段如下：

| 字段 | 类型/上限 | 含义 |
| --- | --- | --- |
| `topics` | 最多 2 个 TopicRef | 已确认的公开主题；不代表身份或权限 |
| `pending_topics` | 最多 2 个 TopicRef | 指代歧义时用于询问的有效候选，不自动成为已确认主题 |
| TopicRef 的 `knowledge_id/customer_type` | 受控 ID / 原对象枚举 | 保留旧字段 |
| TopicRef 的 `knowledge_version/source_fingerprint` | 可选版本 / 来源摘要 | 新写入必须齐全并由后端生成；旧记录允许缺失，但不得据此猜测旧来源仍有效 |
| `clarification_status` | idle / awaiting / exhausted / cancelled | 澄清状态，不复用阅读导航状态 |
| `clarification_attempts` | 严格整数 0–2 | 同一未解决歧义已经发出的澄清次数 |

不保存模型思维过程、完整历史副本、原始敏感输入、账户信息或浏览器画像。所有字段随会话自创建起固定 7 天到期及级联清理。

旧 `{}` 和旧 `topics/clarification_attempts` 可读取。旧已用次数必须保留，不重置；缺少新状态时，次数 1 映射 awaiting，次数 2 映射 exhausted，次数 0 映射 idle。旧答复/消息无新增字段时显示“历史记录，处理方式未细分”，不推断其为新版真实结果。

旧 TopicRef 缺少版本/摘要时，只有同会话现有有效导航中对应的知识编号、版本和摘要全部匹配，才补足主题关联。无法证明原来源时保留历史，但停止自动指代续接，提示明确主题后重新建立引用；不把当前新版来源追认成旧主题。旧会话 ID、期限、消息和原导航不得删除或改号。这是来源有效性保护，不作整库清空或重置。

### 6.2 流转规则

| 当前状态/事件 | 下一状态与持久化行为 |
| --- | --- |
| 明确公开新问题 | 后端校验候选与来源，回答成功建立 1–2 个主题，清空已解决澄清次数；未知业务不能强行匹配 |
| 有效单主题追问 | 当前问题原样参与判断；复核对象、开关、版本、摘要及有效期；具体信息缺失仍可保留有效主题 |
| 对象/指代歧义，次数 0 或 1 | 分别发出第 1 或第 2 次具体提示，计数增加并处于 awaiting；可保留经复核的待选候选 |
| 第 2 次提示后的补充足够明确 | 正常回答，转 idle；不得因为已到 2 次拒绝清楚的新信息 |
| 第 2 次提示后的补充仍不足 | 转 exhausted，说明无法确定，提供现有主题选择/取消，不发第 3 次同一歧义的自动提示 |
| exhausted 中仍作模糊改写 | 维持 exhausted 和次数，不靠改写、刷新或重启重置 |
| 明确纠正 | 当前明确纠正优先；排除被否定的旧主题。“你理解错了”未给替代主题时澄清，不能自动猜测 |
| 两个明确公开问题 | 各自生成带对象及来源的 AnswerPart；同时保留两主题；后续模糊指代进入澄清 |
| 取消 | 同一原子事务清空普通主题/待选引用，保存 cancelled、原导航 cancelled 及新会话版本；允许历史不变 |
| 知识停用/变版/正文变动/过期 | 引用失效，不把旧主题当新依据；计算后提交前变化返回 409，不写旧答案 |
| 模型失败 | 返回明确 model_unavailable，不保存猜测主题；保留经复核的既有主题、次数/状态，不延长期限或费用额度 |
| 敏感、紧急、人工、私有请求 | 先于普通路由；保护路径不调用模型，按既有边界终止普通主题；紧急提示单独保存，不因取消而关闭 |

敏感检测首先决定哪些文字可保存/发送；安全场景仍能触达固定紧急提示。目录损坏时人工、敏感、紧急、取消及明确私有未接入路径应保持可达。必须检查私有请求与多主题混合输入，不允许公共资料分支绕过私有保护。

### 6.3 并发、取消和提交资格

延续 `expected_revision` 及事务条件更新。计算前、模型后、写入前重查会话归属、期限、来源和开关；旧普通请求遇到新版会话返回 409，不写用户/助手半条记录。紧急事件沿用既有独立优先保存规则。

前端对象/会话切换和取消立即撤销展示资格；原在途取消跟踪与快速切回保护保留。澄清时即使没有阅读卡也可取消，按钮不能只依赖 `navigation.status=reading`。迟到模型调用仍计入预算，但不能恢复已取消主题或污染新对象。取消不隐含关闭安全提示。

保留请求字段、旧路径和旧 Outcome 枚举。无 SSE、上传、银行工具、外部发送或动态 Agent；短请求用普通 JSON，模型总体等待按第三节截断。

| --- | --- | --- | --- |
| POST `/api/v1/sessions` | 原 `customer_type` | 原 SessionInfo | 原 201/401/403/422/503 规则 |
| POST `/api/v1/sessions/{sid}/messages` | 原 `text`（1–2000 字符）、可选 `expected_revision` 及成对的能力/版本字段 | 原 Turn；兼容追加 `consultation`；Answer/AnswerPart 追加处理方式、问题类别及资料覆盖范围，原 text/sources/parts/cards 保留 | 401 无归属；404 不存在/无权/到期；409 会话或来源变更；422 输入错误；503 配置/存储不可用 |
| GET `/api/v1/sessions/{sid}` | 原归属 Cookie | 原 History，追加当前 `consultation`；旧消息补兼容默认，历史卡继续复核 | 原 401/404/503 |

统一错误保持 `{"error":{"code":"...","message":"..."}}`，不返回堆栈、供应商原文、Key、完整用户输入或预算数据库内容。模型异常作为已处理的 Turn 返回 `answer.kind=model_unavailable`；请求/存储/并发等错误才走对应 HTTP 错误，不混用二者。

### 7.2 新增视图字段

- `consultation`：`status`、`clarification_attempts`、受控 `topic_ids`、最多两个 `pending_topic_ids`、`can_cancel`、`revision`。不暴露完整历史、来源摘要或身份推断；来源失效的 ID 不作为有效主题展示。
- `Answer.processing` 与 AnswerPart 的同名字段：`rule/model/fallback/legacy`，旧记录缺失默认 legacy。`mode` 仍表示配置模式，不单凭 mode=model 宣称该条调用了模型；实际路由和预算记录决定 processing。
- `Answer.focus` 与 AnswerPart 同名字段：下文受控类别；多个类别的聚合答复可用 general，逐项类别看 parts。
- `Answer.coverage` 与 AnswerPart 同名字段：`overview/partial/none/legacy`。overview 是当前演示概述，不是已验证银行规则；partial 表示有主题说明但所问具体事项无法确认；none 表示无可用依据；旧记录默认 legacy。

这些字段兼容追加，旧前端仍可显示 text/sources。新前端仅显示用户需要的“规则演示/真实模型判断/模型失败”“演示概述/具体事项尚不能确认”等文字，不展示内部契约名称、预算表或技术错误。不同对象的 parts 必须保留各自来源，不只靠聚合 sources 暗示关联。

### 7.3 新模型契约 `consultation-route-v14`

单条当前问题一次输出最多两个公开主题，避免按对象分别付费调用。输入由后端生成：

```json
{
  "question": "会收多少钱",
  "public_object": "personal",
  "topics": [{"id": "personal_opening", "version": "demo-v1"}],
  "pending_topics": [],
  "clarification_attempts": 0,
  "candidates": [{"id": "personal_opening", "title": "个人开户咨询", "keywords": ["开户", "开卡", "借记卡"]}]
}
```

示例只展示格式，不限制真实候选必须单条。默认候选限定当前对象；明确跨对象公开问题允许加入相应对象的适用资料，并由后端保留对象标签，不改变会话归属或授权。失效、停用、无正文或不匹配目录版本的知识不得成为候选/上下文。来源摘要留在后端复核，不发送给模型；不发完整知识正文、全部聊天历史、私有字段或认证内容。

模型输出唯一结构：

```json
{"action":"select","items":[{"id":"personal_opening","focus":"fees"}]}
```

| 字段 | 允许值及校验 |
| --- | --- |
| `action` | select / clarify / unknown |
| `items` | select 时 1–2 项；clarify/unknown 时空数组；对象由候选映射取得，不由模型声明身份 |
| `id` | 本次候选 ID，唯一，不得含候选外资料或工具 |
| `focus` | general / materials / channel / fees / qualification / timing / download / guarantee |

模型不能返回正文、网址、金额、权限、工具名称或自主调用步骤。后端强校验字段类型、枚举、action/items 一致性、候选集合、对象适用性及来源状态；接受纯 JSON 或完整包裹的 JSON 代码块，不用正则从任意说明中捞出片段。非法字段/类型/候选 ID 属无效结果，有限重试后失败；超过两个明确主题、重复条目等数量/质量问题单独记录并提示分批/澄清，不为凑格式连续重试，也不截断后宣称完整覆盖。

旧 `ModelSelection={knowledge_id: ...}` 不作为新契约的成功输出，旧解析器与旧回归保留。批量路由不以旧版单 ID 记录假装新契约通过；原费用记录表不扩成新台账，批量选择的完整结构记录在受控验证材料和对应会话答复中。

## 八、Prompt 与后端答案组织

新 Prompt 独立文件、版本 `consultation-route-v14`，要求当前问题优先；有效主题只解决指代，不替代原问题。明确“不是 X，是 Y”排除 X；多主题不得任意挑选；资料外问题返回 unknown；歧义返回 clarify；问题类别用于选择固定缺口提示，不代表资料支持具体事实。

Prompt 给正反例：开户主题下“会收多少钱”选择开户/fees；“不是开户，是定期存款”选择存款；明确个人/企业开户可输出两项；无上下文的“这个怎么办”返回 clarify。反例禁止编造材料、金融数值、已连接人工、候选外编号、猜测身份以及正文/URL。Prompt 不承担费用、安全、权限或状态的最终控制。

规则模式用有限同义表达、否定纠正解析、对象拆分和有效上下文做同样的路由结构；不承诺通用语义理解。明确纠正中的否定片段不能参与正向关键词投票，当前匹配到新主题优先于旧主题。无法可靠拆分时明确澄清，不能为了通过样例追加任意题目到匹配白名单。

后端组织顺序：

1. 读取合法路由，并从当前有效资料映射对象/来源。
2. general 类：回应主题，引用与问题相关的原文句子，保留演示与限制；找不到更细的对应内容时说明仅有概述。
3. materials/channel/fees/qualification/timing：当前六条资料不含可确认的具体清单、渠道、收费、资格或时限，先用固定模板指出该事项无法确认，再引用相关原文说明。不能把“应以正式说明为准”当成已知办理答案。
4. download 类：企业回单资料可支持“当前未接入下载/查询”的演示状态，禁止生成回单或已下载结果。
5. guarantee 类：用固定不承诺表述及相关原文限制，不判断贷款/融资获批或额度。
6. 多个问题分别组织、分别绑定来源和 coverage；某项未知时该项明确无依据，保留可回答部分，不将另一项来源移作背书。

所有业务句子来自原文摘录；固定模板只说明资料范围/未接入状态，不创作银行事实。具体类别仍经后端检查当前问题中的费用、资格、承诺等明确风险表达；模型误分类为 general 不能跳过缺口提示。原卡片可继续阅读完整原文，但首条答复必须回应当前问题，不只重复整条资料。

## 九、最小验收界面

## 十一、产品经理验收清单

以下为开发后操作，当前仍是计划，执行时由 AI 提供可打开的独立验收入口。

1. 打开 AI 提供的本机 V1.4 地址，选择个人服务，看到明确的规则或真实处理方式及演示标记。
2. 输入借记卡咨询，再问“会收多少钱”；看到当前费用问题被回应，资料缺口明确，来源仍属于个人开户。
3. 输入“不是开户，是存款”，看到主题切换；另建会话只说“你理解错了”，应询问要纠正什么。
4. 新会话问“这个怎么办”，连续作模糊补充；最多看到两次澄清，之后提供主题选择/取消。刷新不重新计数；明确输入“个人开户”后可继续。
5. 澄清中点取消，刷新后不恢复旧追问；新的明确问题可正常咨询。普通取消不会关闭安全提示。
6. 问“个人开户和企业开户各要了解什么”，看到两项来源；再问“那还需要什么”，应要求明确所指对象/主题。
7. 切到企业，检查企业开户、对账回单和融资资料；问下载或获批，不出现真实回单、成功状态或保证审批承诺。
8. 仅用 AI 给出的虚构敏感样例核对屏蔽；人工、余额、紧急问题保持既有保护，无连接人工/冻结/办理成功的虚构提示。
9. 按 AI 引导重启独立验收服务，核对主题、澄清次数和取消恢复；期限不被追问延长。无需产品经理找数据库、手册或执行技术指令。
10. 看过每条新版真实答案后给一个整体 1–3 分，标出不能接受项；不拆填五项评分、不沿用 V1.3 的 3 分。
